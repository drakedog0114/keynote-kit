# RFC 0001 · 用「声明式页面」重做 keynote-kit 的编辑模型

状态：**草案（待评审）** · 2026-11-01 · 作者：Drakedog + DeepSeek Harness

---

## 1. 为什么要改

现在的 keynote-kit 是**命令式**的：41 个 MCP 工具，每个只干一件事（加文本、加形状、改样式、对齐……）。
这是照着 iwork-mcp 的形状抄的，而 iwork-mcp 本身又是照着 AppleScript 的原子动词抄的。

做完飞书 Slides 的对照测试后，问题很清楚了：

| 症状 | 根因 |
|---|---|
| 生成一页要 8–12 次调用，token 与时间都浪费 | 没有一个"整页"的原语 |
| 出错时不知道错在哪（`-1728`、`-1719`） | 错误没有上下文 |
| 写成功后内容可能丢（静默失败） | 没有事务 / 回读 |
| 同一页反复改会互相踩 | 没有版本或结构指纹 |
| 每个调用方都要自己算坐标和 z 序 | 没有布局层 |

飞书的 SML 恰好是**声明式**的：一页就是一段 XML，元素顺序即 z 序，样式是属性，
提交后有 `revision_id`。这套模型在工程上明显更稳。

**所以迭代方向不是"再加 10 个工具"，而是换一层抽象。**

---

## 2. 目标（可验收）

| 指标 | 现在 | 目标 |
|---|---|---|
| 生成一页 PPT 的调用次数 | 8–12 次 | **1 次**（`kk_page`） |
| 单页生成耗时 | 3–5 s | **< 1.5 s** |
| 静默失败率 | 有（图片路径错、索引错） | **0**（写后校验，失败即回滚） |
| MCP 工具数 | 41 | **≤ 14** |
| 错误信息 | `Keynote error -1728` | `NotFound: 第 3 页没有文本元素"标题"` |
| 页面背景 | 不支持 | 支持（仿真实现） |

## 3. 核心设计：把页面变成数据

### 3.1 Page Spec（新的一等公民）

```json
{
  "slide": 4,
  "background": { "type": "solid", "color": "#F7F5F0" },
  "elements": [
    { "type": "text", "id": "title", "text": "五类角色，权限逐层收敛",
      "box": [140, 110, 1640, 150],
      "style": { "size": 56, "font": "Songti SC Bold", "color": "#2B2420", "align": "left" } },

    { "type": "text", "id": "body", "text": "总部运营：…\n区域负责人：…",
      "box": [140, 300, 1640, 640],
      "style": { "size": 26, "color": "#2B2420", "lineSpacing": 1.35 } },

    { "type": "image", "id": "chart", "path": "/tmp/bar.png", "box": [110, 280, 860, 480] },

    { "type": "table", "id": "t1", "box": [150, 600, 1620, 420],
      "data": [["业务域", "承接"], ["准入", "全定制"]],
      "style": { "size": 16, "headerColor": "#1F3A5F" } }
  ]
}
```

**元素顺序 = z 序**（先插入的在下面），这一条直接抄飞书——它解决了 Keynote 没有 z 序 API 的问题：
既然只能靠插入顺序控制层级，那就把顺序变成规范。

### 3.2 一个工具做完整页

```
kk_page(doc, slide, spec)  →  { ok, slide, applied, verified, revision }
```

内部执行链（全部在一处完成，调用方看不见）：

```
1. 事务开始：快照当前页元素（类型/位置/文本）
2. 清空或保留（mode: replace | append）
3. 背景：渲染纯色/图片 PNG → 作为第一张图插入（保证在最底层）
4. 逐元素：JXA 创建 → AppleScript 定位 → JXA 样式（按内容匹配，不靠索引）
5. 回读校验：元素数量 + 每个元素的位置/尺寸在容差内
6. 不符 → 删除本次新增元素 → 抛错（回滚）
7. 计算页面指纹，写入 revision
```

### 3.3 样式模型统一（顺手修掉 format_shape）

现在 `format_shape` 会报 `-1728`，因为它在索引上找元素。新模型里：

- 所有样式通过一个 `apply_style(element, style)` 完成
- 元素定位一律**按内容匹配**（文本内容 / 文件 basename），不用索引
- 字体名做白名单校验（`Songti SC Bold` 合法、`SongtiSC-Bold` 非法），非法时给出建议值

### 3.4 背景：用"底层图"仿真

Keynote 没有页面背景 API，但**插入顺序 = 层级**，所以：

```
background(solid #F7F5F0) → 生成 1×1 或 8×8 的 PNG（按色值缓存）→ 拉伸到整页 → 第一个插入
```

这让 keynote-kit 第一次具备"每页独立背景"的能力——和飞书对齐。
缓存放在 `~/.cache/keynote-kit/bg/<hex>.png`，避免重复 IO。

### 3.5 错误语义化

| Keynote 原始错误 | 映射 | 附带信息 |
|---|---|---|
| `-1728` 不能获取对象 | `NotFound` | 文档名 / 页码 / 元素 id |
| `-1719` 无效的索引 | `IndexOutOfRange` | 页码 / 元素数 / 请求索引 |
| `-10000` 处理程序失败 | `VerbUnsupported` | 该动词在 15.x 已损坏，给出替代写法 |
| `-1700` 不能转换类型 | `Coercion` | 通常是字体名或枚举值写错，给出合法候选 |
| 文件不存在 | `MissingAsset` | 路径 + 是否相对路径 |

## 6. 风险与不做的事

| 风险 | 应对 |
|---|---|
| Keynote 的 `-10000` 类错误可能让 App 卡死 | 事务前先 `verify` 文档存活；连续 2 次超时即中止并提示重启 |
| 全文匹配定位在同页重复文本时会歧义 | spec 里强制 `id` 唯一；同文本追加序号后缀 |
| 背景图会让文件变大 | 纯色背景用 8×8 PNG，几乎零成本 |
| 声明式模型掩盖了 Keynote 的坑 | 每个 spec 元素对应一份"操作履历"，出问题能打印实际执行序列 |

**明确不做**：

- 不做"像素级还原飞书 SML"——Keynote 没有 chart/背景/单元格底色，硬做只会更难维护
- 不引入模板引擎（Jinja 之类）——JSON spec 已经够表达，模板语言会让 agent 更难用对
- 不追求 1:1 兼容 iwork-mcp 的调用约定——那套是历史包袱

## 7. 一个直观对比

同样是"三卡 + 标题"一页：

**现在（9 次调用）**
```
add_slide → add_text ×2 → add_image → position_item ×4 → align_items → verify
```

**改造后（1 次调用）**
```json
kk_page(doc, 3, {
  "elements": [
    {"type":"text","text":"三个补齐点","box":[150,120,1200,100],"style":{"size":56,"font":"Songti SC Bold"}},
    {"type":"image","path":"cards.png","box":[150,330,1560,340]},
    {"type":"text","text":"精确排版","box":[190,380,400,60],"style":{"size":38}},
    {"type":"text","text":"原生表格","box":[730,380,400,60],"style":{"size":38}},
    {"type":"text","text":"图表能力","box":[1270,380,400,60],"style":{"size":38}}
  ]
})
```

调用方只需要想"这页长什么样"，不需要想"先加什么后加什么"。

## 9. 实测结果（P0 已落地，2026-11-01）

实现位置：`keynote_kit/page.py` + MCP 工具 `kk_page` / `kk_page_validate`。

### 9.1 达成的

| 项 | 结果 |
|---|---|
| 单页调用次数 | **1 次 `kk_page`**（原 8–12 次） |
| 写后校验 | 自动回读，位置偏差 > 20pt 即报错 |
| 回滚 | `mode=replace` 时校验失败会清空本页；spec 非法则不写入 |
| 每页背景 | **可用**（纯色 8×8/192×108 PNG 缓存 + 整页图，或直接给图片） |
| 元素顺序 = z 序 | 可用（先插背景，再按 spec 顺序） |
| 表格 | 可用（原生表格 + 单元格写入） |

### 9.2 实测耗时（12 页测试稿，含背景）

| 页型 | 元素数 | 耗时 |
|---|---|---|
| 封面（标题+副标题+背景） | 3–4 | 2.1–3.7 s |
| 三卡页 | 11 | 4.7–7.6 s |
| 表格页 | 3 | 2.0–5.3 s |

**每元素约 0.4–0.6 s**，与元素数近似线性。

### 9.3 没达成的（重要）

1. **1.5 s/页 的目标不现实**。瓶颈不是 AppleEvent 数量，而是 Keynote 对每个元素的
   版面重算：几何设值本身只 0.12 s/元素，但叠加创建+样式+回读后稳定在 0.4–0.6 s/元素。
   目标修正为：**≤6 元素 ≤2.5 s；每元素 ≤0.6 s**。
2. **工具面收敛（41→12）未做**，当前 43 个（新增 2 个），旧工具仍在。
3. **文本对齐不可设**：`alignment` 只有表格单元格支持，text item 报 -1700，
   新建文本会继承主题的默认对齐（居中）。
4. **形状没有填充色**：Keynote 没有 shape fill API，`type: "shape"` 目前只能当描边空盒，
   彩色卡片必须用 PNG（`charts` / `diagrams` 或预渲染）。

### 9.4 过程中确认的三个 Keynote 行为

- **JXA 设 `position` 静默失效**（返回 ok，读回 0,0），几何必须走 AppleScript。
- **JXA 与 AppleScript 看到的集合顺序不同**：JXA 认为新元素在末尾，AppleScript 里
  占位符可能排在后面。所以不能跨语言复用索引，只能在 AppleScript 内部匹配。
- **`object text of text items of s` 逐项读取很贵**（每项一次事件）；
  用 `as list` + 文本项分隔符一次取回，再在 Python 侧匹配，是唯一快且稳的路径。

### 9.5 下一步（P1）

1. 加 `type: "card"`：按颜色/圆角/尺寸渲染 PNG 卡片（补上 Keynote 没有填充色的缺口）
2. 文本对齐：尝试 paragraph 层属性或主题占位符，失败则记录为已知限制
3. 工具面收敛到 12 个，旧工具标记 deprecated
4. 用 `kk_page` 重建某宠物品牌 v3 的 15 页做回归

## 10. P1 落地：`card` 类型（2026-11-01 同日）

### 10.1 问题

Keynote 的 `shape` **没有填充色**（无 API），文本也**不能设置对齐**（`alignment` 只支持表格
单元格，text item / paragraph 都报 -1700）。这两条让「飞书那种彩色卡片」在 Keynote 里做不到。

### 10.2 做法：卡片连文字一起渲染成 PNG

```json
{
  "id": "c1", "type": "card", "box": [150, 290, 500, 400],
  "style": { "fill": "#FFFFFF", "radius": 26, "border": "#D9CFBE", "borderWidth": 2 },
  "text": {
    "title": "整页 Spec", "body": "一页一个 JSON，元素顺序即 z 序……",
    "titleSize": 30, "bodySize": 17, "gap": 18, "padding": 38,
    "titleColor": "#2B2420", "bodyColor": "#6E6259",
    "align": "left", "valign": "center"
  }
}
```

- 用 Pillow 渲染圆角矩形 + 标题（Songti，衬线）+ 正文（Hiragino Sans GB，无衬线）
- 正文按字符贪心换行，支持 `\n`、`lineHeight`、`align`、`valign`
- 2 倍尺寸渲染，插入时缩放到 box，保证清晰
- 按 (填充/尺寸/圆角/文字参数) 哈希缓存到 `~/.cache/keynote-kit/cards/`

### 10.3 收益

| 项 | 用 shape + 多个 text | 用 card |
|---|---|---|
| 三卡页元素数 | 11–14 | **5** |
| 三卡页耗时 | 4.7–7.6 s | **1.6–1.8 s** |
| 可设对齐 / 行高 / 颜色 | ❌ | ✅ |
| 文字可在 Keynote 里二次编辑 | ✅ | ❌（已栅格化） |

**12 页测试稿整体：平均 2.21 s/页（1.61–2.90 s）**，比 P0 的 4.04 s/页快 45%，
主要来自元素数减少。

### 10.4 取舍声明

卡片文字栅格化 = 失去可编辑性。适合「一次成型、以出片为主」的场景；
需要客户自己改文案的稿子，仍应使用 text 元素（接受默认对齐）。

## 11. P2 回归验证：用 v3 真实稿子往返（2026-11-01）

### 11.1 方法

拿真实交付稿 `某宠物品牌B2B采购方案-v3-米色底.key`（15 页）做往返：

1. 逐页读成 spec（文本 + 位置 + 字号 + 字体 + 颜色）
2. 用 `kk_page` 重建到一份新稿
3. 两稿都导出逐页 PNG，比对像素差；同时比对元素结构

其中 3 页含图片/表格（P5、P7、P11），本次跳过，比对 12 页。

### 11.2 结果

**布局保真：12/12 页完全一致**

| 指标 | 结果 |
|---|---|
| 元素数量 | 逐页一致 |
| 文本内容 | 逐页一致 |
| 坐标 (x, y) | 最大偏差 **0 pt** |
| 重建耗时 | 12 页 35 秒（≈2.9 s/页） |

**像素差：10–20（不是 0）** —— 差异全部来自「版式自带、不属于元素」的部分：

- 主题的纸张纹理与渐变底
- 页眉页脚的发丝线（hairline）
- 项目符号的小方块（段落级格式，不在元素模型里）
- 段落级样式（同一文本框里不同行不同字号）

### 11.3 结论

> `kk_page` 是**精确的排版层重建**，不是**视觉还原**。

适用：新建页面、按 spec 重排版面、批量生成结构一致的稿子。
不适用：把一份已有 deck 克隆到新主题（装饰与段落格式无法枚举）。

这也解释了 P0 阶段的一个错误预期：我原以为「重建 15 页并像素一致」可以当验收标准，
实际应改为「**布局一致 + 元素/文本/坐标零偏差**」，像素差只作为回归告警阈值（>25 视为异常）。

### 11.4 顺带产出：`kk_extract_page`

往返验证的过程固化成了工具：

```python
kk_extract_page(doc, slide, background="#F4EBDD")
# → {"slide": 4, "spec": {elements: [...]}, "images": 0, "tables": 0}
```

用途：把已有页面读成 spec，改几处后 `kk_page` 写回；或把老稿的一页搬到新 deck 做起点。
注意它同样只取元素，不取装饰。

## 12. P3：`chart` 与 `diagram` 成为声明式元素（2026-11-01）

### 12.1 新增两种元素类型

```json
{"id": "ch", "type": "chart", "box": [150, 170, 1620, 760],
 "chart": {"kind": "bar|line|donut", "labels": [...], "values": [...],
           "series": {...}, "title": "...", "color": "#1F3A5F", "suffix": "d"}}

{"id": "dg", "type": "diagram", "box": [130, 140, 1660, 880],
 "diagram": {"kind": "swimlane|hierarchy|integration", "title": "...",
              "stages": [...], "lanes": [...], "highlight": [[1, 2]],
              "palette": "paper|blue"}}
```

内部调用 `charts.*` / `diagrams.*` 渲染 PNG，按配置哈希缓存到
`~/.cache/keynote-kit/fit/`，再当作图片插入。

### 12.2 两处精度修正

| 问题 | 修正 |
|---|---|
| 图表/信息图模板自带大片透明留白，塞进 box 后内容偏小 | 渲染后按 alpha bbox **裁掉透明边** |
| 图片类元素被 box 强制拉伸变形 | 长宽比偏差 >5% 时按 PNG 真实比例**修正高度** |

### 12.3 效果

- 一页 = 标题 + 图表 + 泳道图，4 个元素，2–3 秒
- 图表/泳道图与卡片同一套 spec 语法，不用再手动 `charts.bar_chart()` + `add_image()`

### 12.4 注意

- `diagram` 信息密度高，**大于半页**才有可读性；半页以下建议直接截图或用 card 承载
- 图表文字由 matplotlib 渲染，字体走系统回退（Hiragino 无 bold 时会降级），不影响观感

|---|---|---|---|
| 1 | 封面（标题 + 副标题） | 4 | 3.90 s |
| 2 | 卡片 ×3 + 柱状图 + 卡片 | 6 | 4.53 s |
| 3 | 原生表格 | 3 | 1.83 s |
| 4 | 泳道图（整页） | 2 | 1.26 s |
| 5 | 三卡总结 | 5 | 3.87 s |
| 6 | 金句页 | 3 | 2.40 s |

**总计 17.8 秒，平均 2.97 s/页**，一次跑通、全部校验通过、无回滚。

### 13.3 结论：这套模型经得起考验

| 目标 | 结果 |
|---|---|
| 覆盖场景更多 | 元素类型 4 → **6**（+card / +chart / +diagram） |
| 效率更高 | 调用 8–12 → **1**；耗时 3–5 s → **2.2–3 s** |
| 质量精度更好 | 布局 **0 pt 偏差**；长宽比自动修正；图表裁掉透明边 |
| 可靠性 | 写后回读 + 回滚；spec 校验前置 |

已知边界（不在本 RFC 解决范围）：主题装饰、段落级格式、文本对齐不可脚本化。

## 14. P4：可编辑性与排版质量（目标调整为「可编辑 + 精度」优先）

### 14.1 问题

`card` 把文字栅格化，**牺牲了可编辑性**。而裸 `TextItem` 又拿不到主题的对齐、项目符号、
段间距——Keynote 的 `alignment` 只对表格单元格开放（text item / paragraph 都报 -1700）。

### 14.2 方案：写进母版占位符（slot）

```json
{"type": "text", "slot": "title", "text": "一个底座，一个定制点",
 "box": [150, 110, 1620, 110]}
{"type": "text", "slot": "body",
 "text": "底座：沿用现有商城\n定制点：采购价注入\n四端：小程序 + PC 后台",
 "box": [170, 300, 1560, 500]}
```

流程：`add_slide("<带标题与项目符号的母版>")` → `apply_page` 找到该页占位符
（按宽度过滤幽灵、按 y 排序、按 (x,y,w) 去重）→ 写入文本 + 定位。

**收益**：主题的对齐、项目符号、段间距、纸纹背景、发丝线全部保留，文字仍可编辑。

### 14.3 两个必须知道的约束

1. **不能清空页面**：`clear_slide` 会连占位符一起删掉，所以 slot 模式强制走 append。
2. **不能插整页背景图**：占位符在图层底部，新插入的背景图会盖住它；背景交给母版。

### 14.4 与 card 的分工（重要）

| 场景 | 用法 | 可编辑 |
|---|---|---|
| 标题 / 正文 / 列表 | `text` + `slot`（母版占位符） | ✅ |
| 需要精确对齐的图文块 | `text`（裸文本框，居中默认） | ✅ |
| 彩色卡片 + 卡片内文字 | `card`（栅格化） | ❌ |
| 图表 / 信息图 | `chart` / `diagram`（本身就是图） | ❌ |

结论修正：**默认用 slot 写文字，card 只用于需要填充色块的装饰性容器**。
